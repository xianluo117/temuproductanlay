# 智猴 ERP 协议登录方案

## 1. 结论

智猴 ERP 可以完全通过 HTTP 协议完成登录，无需浏览器参与登录流程。

已完成实际验证：

- 协议获取验证码成功。
- Base64 PNG 验证码在内存中解码成功。
- OCR 成功识别数学算式。
- 程序自动计算验证码答案。
- 协议提交账号、密码和验证码成功。
- 登录接口成功返回访问令牌。
- 使用访问令牌调用会话接口成功。
- 会话返回账户与登录账户一致。

本次验证在第 `1` 次尝试成功，OCR 识别算式为：

```text
2+1
```

自动计算答案为：

```text
3
```

推荐架构：

> HTTP 协议负责验证码获取、OCR 登录、令牌管理、订单查询和库存查询；CloakBrowser 仅作为人工登录兜底工具。

## 2. 登录流程

完整协议登录流程：

```text
获取验证码
  → Base64 解码
  → 图像预处理
  → OCR 多模式识别
  → 识别结果投票
  → 受限算式计算
  → 提交登录
  → 获取访问令牌
  → 调用会话接口验证令牌
  → 保存有效令牌
```

步骤说明：

1. 请求验证码接口。
2. 获取验证码图片和一次性验证码键。
3. 在内存中解码图片。
4. 使用 OpenCV 生成多个预处理版本。
5. 使用 Tesseract 多模式识别完整算式。
6. 使用 ddddocr 辅助确认数字。
7. 对多个 OCR 结果进行投票。
8. 只接受符合固定格式的数学表达式。
9. 使用受限计算器得到答案。
10. 提交账号、密码、验证码键和答案。
11. 从登录响应中读取访问令牌。
12. 使用令牌调用会话接口。
13. 验证会话账户与目标账户一致。
14. 将令牌交给订单和库存协议客户端。

## 3. 验证码接口

### 3.1 基本信息

| 项目     | 内容                                                       |
| -------- | ---------------------------------------------------------- |
| 接口用途 | 获取数学图片验证码                                         |
| 请求地址 | `https://api-cn.zhfulfill.com/erp/dealer/passport/captcha` |
| 请求方法 | `GET`                                                      |
| 鉴权     | 不需要                                                     |
| 响应格式 | JSON                                                       |

### 3.2 响应结构

```json
{
  "code": 200,
  "data": {
    "image": "<Base64 PNG>",
    "key": "<一次性验证码键>"
  },
  "message": "success"
}
```

字段说明：

| 字段         | 说明                                        |
| ------------ | ------------------------------------------- |
| `code`       | 业务状态码                                  |
| `data.image` | Base64 编码的 PNG 图片，不包含数据 URI 前缀 |
| `data.key`   | 与当前验证码图片绑定的一次性键              |
| `message`    | 业务消息                                    |

### 3.3 使用要求

- 验证码图片和验证码键必须成对使用。
- 不能将新图片的答案提交给旧验证码键。
- 验证码失败后应重新获取图片和键。
- 不建议重复使用已经提交过的验证码键。
- 验证码图片只在内存中处理，不保存到普通日志目录。

## 4. 登录接口

### 4.1 基本信息

| 项目         | 内容                                                               |
| ------------ | ------------------------------------------------------------------ |
| 接口用途     | 提交账号、密码和验证码                                             |
| 请求地址     | `https://api-cn.zhfulfill.com/erp/dealer/passport/loginHasCaptcha` |
| 请求方法     | `POST`                                                             |
| Content-Type | `application/json;charset=UTF-8`                                   |
| Cookie 依赖  | 当前未发现                                                         |
| 动态签名     | 当前未发现                                                         |
| 请求体加密   | 当前未发现                                                         |

### 4.2 请求结构

```json
{
  "account": "<账号>",
  "password": "<密码>",
  "captchaParam": {
    "captchaKey": "<验证码键>",
    "captchaCode": "<数学计算结果>"
  }
}
```

参数说明：

| 参数                       | 说明                             |
| -------------------------- | -------------------------------- |
| `account`                  | ERP 登录账户                     |
| `password`                 | ERP 登录密码                     |
| `captchaParam.captchaKey`  | 验证码接口返回的一次性键         |
| `captchaParam.captchaCode` | 数学算式的计算结果，按字符串提交 |

### 4.3 成功响应

```json
{
  "code": 200,
  "data": "<访问令牌>",
  "message": "success"
}
```

登录接口的 `data` 字段直接包含访问令牌。

## 5. 会话验证接口

### 5.1 基本信息

| 项目         | 内容                                                            |
| ------------ | --------------------------------------------------------------- |
| 接口用途     | 验证访问令牌并加载用户会话                                      |
| 请求地址     | `https://api-cn.zhfulfill.com/erp/dealer/passport/access/token` |
| 请求方法     | `POST`                                                          |
| Content-Type | `application/json;charset=UTF-8`                                |
| 鉴权请求头   | `x-access-token`                                                |

### 5.2 请求头

```http
Accept: application/json, text/plain, */*
Content-Type: application/json;charset=UTF-8
x-access-token: <登录接口返回的访问令牌>
```

### 5.3 请求体

```json
{}
```

### 5.4 验证条件

协议登录不能只以“登录接口返回令牌”作为最终成功条件，还应检查：

1. 会话接口 HTTP 状态正常。
2. 会话接口业务 `code` 为 `200`。
3. 会话数据包含用户信息。
4. 返回账户与目标登录账户一致。

如果账户不一致，应立即丢弃令牌并停止任务。

## 6. 访问令牌

### 6.1 使用方式

登录接口返回的令牌通过以下请求头传递：

```http
x-access-token: <有效访问令牌>
```

以下接口已确认使用同一鉴权方式：

- 会话验证接口
- 订单分页接口
- 库存分页接口
- 店铺及其他 ERP 业务接口

### 6.2 浏览器存储位置

浏览器登录成功后，令牌保存在 `localStorage`：

```text
hp_erp_token
```

全协议模式不依赖该存储位置，但可以将浏览器内令牌作为人工兜底来源。

### 6.3 令牌安全要求

- 不得硬编码到源代码。
- 不得提交到版本控制。
- 不得打印完整令牌。
- 日志只允许显示首尾各 `4` 位。
- 应优先保存在进程内存或安全凭据存储中。
- 令牌失效后应重新登录，不得无限重试业务接口。

## 7. 验证码 OCR 方案

### 7.1 当前环境

已确认可用组件：

| 组件          | 状态 |
| ------------- | ---- |
| OpenCV        | 可用 |
| Pillow        | 可用 |
| NumPy         | 可用 |
| pytesseract   | 可用 |
| Tesseract OCR | 可用 |
| ddddocr       | 可用 |

Tesseract 安装路径：

```text
C:\Program Files\Tesseract-OCR\tesseract.exe
```

当前 Tesseract 未加入终端 `PATH`，程序应显式配置绝对路径，或由环境变量指定：

```text
TESSERACT_CMD
```

### 7.2 图像预处理

对每张验证码生成以下版本：

1. 灰度图三倍放大。
2. OTSU 二值化。
3. OTSU 反色二值化。
4. 自适应阈值图。
5. 二值图开运算去噪。

放大建议：

```text
fx = 3
fy = 3
interpolation = INTER_CUBIC
```

OTSU 示例：

```python
_, otsu = cv2.threshold(
    enlarged,
    0,
    255,
    cv2.THRESH_BINARY + cv2.THRESH_OTSU,
)
```

### 7.3 Tesseract 配置

限制允许识别的字符：

```text
0123456789+-xX*/=?
```

建议对每个预处理版本执行以下页面分割模式：

```text
6, 7, 8, 10, 11, 13
```

单次 OCR 结果不能直接提交登录。必须收集多个结果并投票。

### 7.4 ddddocr 用途

通用 ddddocr 模型对数字识别有效，但可能遗漏运算符。

推荐用途：

- 提取左右操作数。
- 辅助确认 Tesseract 的数字识别。
- 不单独决定完整数学表达式。

已观察到：

- Tesseract 可以识别完整算式，例如 `8x1=`。
- ddddocr 可能只返回数字，例如 `81`。

因此应以 Tesseract 的完整表达式为主，以 ddddocr 的数字结果为辅助过滤条件。

## 8. OCR 文本标准化

### 8.1 字符映射

| 原始字符   | 标准字符 |
| ---------- | -------- |
| `×`        | `*`      |
| `x`        | `*`      |
| `X`        | `*`      |
| `÷`        | `/`      |
| `—`        | `-`      |
| `_`        | `-`      |
| `=`        | 删除     |
| `?`        | 删除     |
| 空格和换行 | 删除     |

### 8.2 合法格式

只接受以下格式：

```text
整数 + 单个运算符 + 整数
```

正则表达式：

```regex
(-?\d+)\s*([+\-*/xX])\s*(-?\d+)
```

不符合固定格式的 OCR 结果必须丢弃，不能尝试猜测后直接登录。

## 9. 受限算式计算

### 9.1 支持运算

- 加法：`+`
- 减法：`-`
- 乘法：`*`、`x`、`X`
- 除法：`/`

### 9.2 安全要求

禁止直接使用以下方式计算 OCR 文本：

```python
eval(ocr_text)
```

必须使用受限解析器：

1. 正则提取左操作数。
2. 正则提取单个运算符。
3. 正则提取右操作数。
4. 根据白名单运算符执行对应分支。

除法要求：

- 除数不能为 `0`。
- 当前实现只接受整数整除。
- 非整除结果应视为识别不可靠，重新获取验证码。

## 10. OCR 投票策略

### 10.1 候选生成

候选来源：

```text
图像预处理版本 × Tesseract PSM 模式
```

当前组合数量：

```text
5 个图像版本 × 6 个 PSM 模式 = 30 个候选来源
```

### 10.2 候选过滤

候选必须：

- 符合固定算式格式。
- 运算符属于白名单。
- 左右操作数为有效整数。
- 除法满足安全规则。

### 10.3 投票要求

- 对标准化后的完整表达式计票。
- 至少需要 `2` 个来源识别出相同表达式。
- 如果 ddddocr 能可靠提取两个数字，优先保留数字一致的 Tesseract 候选。
- 没有可靠候选时重新获取验证码。

## 11. 重试策略

### 11.1 推荐次数

默认最大验证码尝试次数：

```text
8
```

可通过环境变量配置：

```text
ZHIHOU_LOGIN_MAX_ATTEMPTS
```

### 11.2 重试条件

以下情况重新获取验证码：

- OCR 没有形成完整表达式。
- 投票数不足。
- 运算符无法识别。
- 除法不满足安全规则。
- 服务端明确返回验证码错误。
- 验证码键过期。

以下情况立即停止：

- 账号或密码错误。
- 账户被禁用。
- 登录接口参数结构变化。
- 会话接口返回账户不一致。
- 服务端持续拒绝请求。

### 11.3 网络错误

- 连接超时：有限次数重试当前步骤。
- 响应超时：有限次数重试当前步骤。
- `429`：退避后重试。
- `5xx`：指数退避，最多重试 `3` 次。
- `401` 或 `403`：重新登录，不重试原业务请求。

## 12. 环境变量

协议登录验证器使用以下环境变量：

| 变量                        | 必需 | 说明                         |
| --------------------------- | ---- | ---------------------------- |
| `ZHIHOU_ERP_ACCOUNT`        | 是   | ERP 登录账户                 |
| `ZHIHOU_ERP_PASSWORD`       | 是   | ERP 登录密码                 |
| `ZHIHOU_LOGIN_MAX_ATTEMPTS` | 否   | 最大验证码尝试次数，默认 `8` |

示例只说明变量名称，不应将真实凭据写入脚本或文档。

## 13. 当前验证器

协议登录验证器：

[`tools/verify_protocol_login.py`](../tools/verify_protocol_login.py)

模块职责：

- 请求验证码。
- Base64 内存解码。
- OpenCV 多版本预处理。
- Tesseract 多模式识别。
- ddddocr 数字辅助识别。
- OCR 候选投票。
- 受限数学计算。
- 提交登录。
- 获取访问令牌。
- 调用会话接口验证令牌。
- 验证返回账户。
- 脱敏输出令牌。

该文件目前属于协议可行性验证器。正式业务实现时，应将职责拆分为独立模块，避免单个文件持续扩大。

## 14. 推荐正式模块结构

```text
src/
  auth/
    captcha-api
    captcha-image-processor
    captcha-ocr
    captcha-expression-parser
    login-api
    session-api
    token-provider
    login-service
  client/
    erp-http-client
  config/
    settings
  security/
    secret-provider
    log-redactor
```

职责说明：

| 模块                        | 职责                             |
| --------------------------- | -------------------------------- |
| `captcha-api`               | 获取验证码图片和键               |
| `captcha-image-processor`   | 图像放大、二值化和去噪           |
| `captcha-ocr`               | Tesseract 与 ddddocr 识别及投票  |
| `captcha-expression-parser` | 标准化、校验和计算数学表达式     |
| `login-api`                 | 提交登录请求                     |
| `session-api`               | 验证令牌和账户                   |
| `token-provider`            | 保存、提供和更新令牌             |
| `login-service`             | 编排完整登录和重试流程           |
| `erp-http-client`           | 统一超时、请求头、重试和错误处理 |
| `secret-provider`           | 从环境变量或凭据存储读取账号密码 |
| `log-redactor`              | 对令牌、账户及响应进行脱敏       |

## 15. 安全要求

### 15.1 凭据

- 账号和密码不得硬编码。
- 不得提交到 Git。
- 不得输出登录请求体。
- 不得在异常堆栈中包含密码。
- 建议从 Windows 凭据管理器、环境变量或专用密钥服务读取。

### 15.2 验证码

- 图片只在内存中处理。
- 默认不保存验证码图片。
- 调试保存图片时必须使用受控临时目录，并在任务后清理。
- 验证码键不得写入长期日志。

### 15.3 令牌

- 不输出完整令牌。
- 日志最多保留首尾各 `4` 位。
- 不将令牌写入普通配置文件。
- 令牌失效后立即从缓存移除。

### 15.4 会话响应

会话接口可能返回个人资料和账户信息：

- 禁止打印完整响应。
- 只读取验证所需字段。
- 日志只记录用户 ID 或账户匹配布尔值。
- 不保存身份证件、联系方式或地址等字段。

## 16. 与订单和库存协议的关系

登录成功获得的访问令牌可以直接用于：

- 订单协议：[`docs/order-protocol.md`](order-protocol.md)
- 库存协议：[`docs/inventory-protocol.md`](inventory-protocol.md)

统一调用关系：

```text
协议登录
  → token-provider
      → 订单协议客户端
      → 库存协议客户端
      → 其他 ERP 协议客户端
```

订单和库存模块不应自行登录，应统一通过 `token-provider` 获取有效令牌。
